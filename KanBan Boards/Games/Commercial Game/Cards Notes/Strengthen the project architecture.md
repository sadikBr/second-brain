- Finish the Arena script move and keep its folder/namespace consistent.
- Organize features by ownership instead of broad type once the project grows—for example `features/isotopes`, `features/run`, `features/hud`.
- Keep each reusable scene close to its script and its dedicated assets where practical; this aligns with Godot’s recommended scene-oriented organization. [Godot project organization](https://docs.godotengine.org/en/latest/tutorials/best_practices/project_organization.html)
- Create a `GameConstants` or configuration resource for shared tuning values.
- Move isotope stats into data resources rather than hard-coded fields.
- Create `IsotopeData` resources for tier, sprite, lifespan, value, movement properties, effects, and rules.
- Separate gameplay state from visuals: the isotope should expose state; visuals should react to it.
- Replace broad global input handling with object-specific input or a central drag controller.
- Add a `PauseManager`.
- Add an `AudioManager`.
- Add a `SaveManager` only once there is progress/settings worth saving.
- Use named collision-layer constants or a documented layer map.
- Add a README with setup, controls, gameplay premise, scene map, and build instructions.
- Add a changelog.
- Maintain a short architecture document as systems multiply.
- Keep the project buildable after every change; your current C# build already succeeds cleanly.
